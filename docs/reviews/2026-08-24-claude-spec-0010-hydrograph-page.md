## Summary

This branch builds spec 0010 slice 2 end to end: the bitemporal observation store, two baselines, prediction intervals conditioned on regime, the seeding hindcast that fills those intervals from a bulk-imported archive without leaking future information, and the public dashboard. The forecasting core (`apps/streamflow`) is unusually rigorous: every raw SQL query with a DISTINCT ON reduction is paired with a pure TypeScript oracle, a statement-level test that pins the exact SQL text and parameter order, and a hand-run script that checks the two agree against a real database. I traced the knowability-axis change (AC-H1–AC-H9) through `as-of.ts`, `observations.repository.ts`, `bucket.ts`/`bucket.repository.ts`, and `score.repository.ts` line by line against the child spec and found the implementation matches the Decision precisely, including the two already-known spec/code tensions noted in `verify.md` (AC-H6/AC-H4, and the unseeded footnote), which I did not re-litigate. The append-only invariant holds: a grep across all production call sites shows no `.update()`/`.delete()` ever reaches `Observation`, `Prediction`, or `Score`. `index.ts` exports a read-only surface, and the Next.js page keeps a clean server/client boundary. The one real gap is on the web side: the new interactive/branching code (`HydrographPanel`'s fetch race-guard and the `/api/observations` route's validation branches) ships with no tests at all, despite the project's own Jest+RTL convention being used for comparable client components elsewhere in `apps/web`.

## Major

### 🟠 New streamflow web layer ships with no tests for its branching and error-handling logic, `apps/web/src/app/streamflow/HydrographPanel.tsx:61`

**Problem**: `HydrographPanel.tsx` has genuine branching logic — a request-id guard against out-of-order responses (`apps/web/src/app/streamflow/HydrographPanel.tsx:59-89`), a 180ms debounce, and a three-state status machine (`idle`/`loading`/`error`) — and none of it is covered by a test. The same is true of `apps/web/src/app/api/observations/route.ts`, the only Next.js API route in this app: its 422-on-invalid-query branch, its 404-on-no-gauge branch, and its success mapping are all untested.

**Why it matters**: Root `AGENTS.md` states "Tests are colocated `.spec.ts`, fully mocked; lint + typecheck + tests gate every commit," and `apps/web` already has an established Jest+RTL convention for exactly this kind of client component (`src/app/beta/BetaPlanner.spec.tsx`, `src/app/beta/PlanDisplay.spec.tsx`, `src/app/internal/components/GradePhotoAdmin.spec.tsx`). The race-guard in particular is the one piece of logic in this component that is easy to get subtly wrong (e.g. a change that compares the wrong ref, or drops the guard in the `catch` path), and a regression there would silently show a visitor a stale hydrograph after they drag the `asOf` slider, with no error surfaced anywhere — neither `tsc` nor `/check verify` would catch it. The observations route's 422/404 paths are the HTTP boundary's actual contract; an untested regression there (e.g. the window-size refine firing on the wrong field, or the wrong status code) would only be caught by someone manually hitting the endpoint.

**Suggested fix**: Add a `HydrographPanel.spec.tsx` covering: a stale response arriving after a newer one is ignored (mock `fetch` with out-of-order resolution), the error state rendering copy when `fetch` rejects or returns non-OK, and the "back to now" reset. Add a `route.spec.ts` for `/api/observations` covering the 422 path (window over 365 days, `from > to`, malformed date), the 404 path (no active gauge), and the success shape. `Hydrograph.tsx`/`SkillChart.tsx` (pure rendering/math, no branching) are lower risk and could reasonably be left to visual verification, but the two files above have exactly the shape of logic the project's own test-adequacy bar (`configured`, "a Major if it's branching logic, error handling, or security relevant") calls out.

## Minor

### 🟡 A hindcast/live prediction collision is silent, `apps/streamflow/src/forecast/hindcast.ts:123-129`

**Problem**: `Prediction`'s unique key is `(gaugeId, modelVersionId, issuedAt, targetTime)` — it does not include `hindcast` (`apps/streamflow/prisma/schema.prisma:199`). If the seeding hindcast's walk is still in flight when a live `PREDICT` cron fires for an overlapping issue slot (the exact sequencing risk the child spec's own Migration plan names: "Running the hindcast after the crons have started... Sequence matters more than speed"), one write wins the unique key via `skipDuplicates` and the other vanishes with no signal anywhere — `written.count` is silently lower than `drafts.length`, and nothing compares the two or logs a mismatch.

**Why it matters**: This is exactly the failure mode the spec's Rollback/Risks section already accepts as a possibility, but the code gives an operator no way to notice it happening in real time; the only symptom is a permanently placeholder-banded prediction discovered much later. Given `runHindcast` already threads an `onProgress` callback for visibility, this is a small, targeted gap in the specific area (error handling/failure modes in the long-running hindcast) this review was asked to scrutinize closely.

**Suggested fix**: After each `prediction.createMany`/`score.createMany`, compare the returned `count` against the row count sent and log a warning (or increment a distinct counter surfaced in the final result) when they differ outside of an expected re-run — that is, when the same walk range hasn't already been run before. Even a simple "skipped N rows this walk expected to write" log line would turn a silent, permanent data quality issue into something visible while the operator is still watching the run, which the spec's own risk notes say they should be.

### 🟡 An interrupted hindcast re-pays the cost of every completed slot on restart, `apps/streamflow/src/forecast/hindcast.ts:67-153`

**Problem**: `runHindcast` always walks `issueSlots(from, to)` from the start of the requested range. Restarting after a crash partway through re-executes `draftPredictions` (including its live `bucketRatiosFromStore` round trips) for every slot already written, even though `skipDuplicates` means none of that work produces a new row.

**Why it matters**: The spec is explicit that this walk is "thousands of sequential round trips against a hosted database... it should be watched rather than left," and calls it "safe to interrupt." That's true for correctness, but not for cost: a transient failure near the end of a multi-hour walk currently means redoing the entire walk's worth of DB round trips rather than resuming near the failure point. This doesn't affect correctness (confirmed via `hindcast.spec.ts`'s "asks the store for the record once" and the idempotency tests), so it's a resilience/efficiency gap rather than a bug.

**Suggested fix**: Either accept an explicit `from` on the CLI so an operator can manually resume past a known-good point (the simplest fix, consistent with the existing `HindcastDeps.from`/`to` already being overridable), or have `runHindcast` query the newest hindcast `issuedAt` already written for the gauge and default `from` to just past it. Not blocking given the CLI already exposes the primitives an operator needs to do this by hand.

## Test coverage

`apps/streamflow`'s 240 tests are thorough and well-targeted at exactly the risk surface this review was asked to focus on: the knowability-axis default/override is pinned at the SQL-statement level for `observationsAsOf`, `scorablePredictions`, and `bucketRatiosFromStore` (byte-for-byte text and parameter-order comparisons, not just behavioral assertions against mocks), the bucket's "one error per prediction, newest revision, tie broken on id" reduction is tested against both axes and against the TS/SQL oracle pair, and `hindcast.spec.ts` directly exercises the failure this child spec exists to fix (a bulk-imported record producing predictions "at every slot" rather than only the last one). `verify-bucket.ts` and `verify-as-of.ts` extend that proof against a real database with fixtures specifically designed to break a query that reads the wrong bound (e.g. `base-target-late`, engineered so only a query still bounding on `actualRecordedAt` would let it through). I did not find any untested branch in the changed `apps/streamflow` logic.

The gap is entirely on the `apps/web` side: `HydrographPanel.tsx`, `Hydrograph.tsx`, `SkillChart.tsx`, `page.tsx`, and `api/observations/route.ts` have zero tests between them, covered in the Major finding above.

## Strengths

- The bitemporal reconstruction is proven three ways for every changed query: a pure TypeScript oracle, a test that pins the literal SQL text and parameter order (so a refactor that quietly changes behavior fails even against a mock that would otherwise agree with anything), and a script that checks the query and oracle agree against a live database with adversarial fixtures. This is a genuinely rare level of rigor for a raw-SQL data layer.
- The append-only invariant is real, not just documented: `grep -rn '\.(update|delete)\('` across all of `apps/streamflow/src` and `scripts/` outside the generated client shows the only mutations anywhere are `pipelineRun.update` (run status), `gauge.update` (the one-time flow-floor freeze), and no-op `upsert`s (`update: {}`) for `Gauge`/`ModelVersion`/the dev fixture script. Nothing ever updates or deletes an `Observation`, `Prediction`, or `Score` row.
- `index.ts`'s read-only export surface is a strong architectural guardrail: the web app physically cannot reach a writer, and a reviewer checking "does the dashboard ever write" only has to check one file.
- The two GitHub Actions workflows are properly hardened for holding the only write credential to a public repo: SHA-pinned actions, empty top-level `permissions`, secrets scoped to individual steps rather than the job, `persist-credentials: false`, and no event triggers an outside contributor could reach.
- `sanitizeError` (unchanged in this diff but load-bearing for it) correctly strips connection strings and `sk_`-prefixed keys before anything reaches the public `PipelineRun.error` field that `runHindcast`'s and `issuePredictions`'s catch blocks write through.
- The Next.js server/client boundary is clean: `page.tsx` does all the heavy Prisma/raw-SQL reads server-side and hands client islands only contract-shaped data (`ObservationsResponse`, the reduced `skill` array) rather than raw Prisma rows, so no internal field ever crosses the serialization boundary.
